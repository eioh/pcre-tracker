# Lessons

## 2026-08-03: 受け入れ確認は「極端なデータ」でも行う（truncate 崩れは短い名前では発火しない）

- **何が起きたか**: クラバト編成サイドバーのツリー化(PR #24)で、短い編成名だけで受け入れ確認して完了報告した。ユーザーの実データ(長い編成名+コピー多数)で行が aside を突き抜けるレイアウト崩れが発覚。原因は D&D 用に新設した行ラッパー div に `min-w-0` がなく truncate チェーンが断ち切られていたこと(PR #20 で直した min-width:auto 問題の再発)。コードレビュー2系統でも検出できなかった(視覚回帰はレビューで見えない)。
- **ルール**:
  1. UI 変更の受け入れ確認では、長い文字列・多数件・空データなど極端なデータを必ず流す。特に truncate/はみ出しは長い名前でしか発火しない。
  2. grid/flex の中間ラッパー要素を新設したら、その下に truncate があるか確認し、あればラッパーに `min-w-0` を付ける(grid/flex アイテムの min-width:auto は nowrap テキストの全幅まで膨張する)。truncate 祖先チェーンの総点検を D&D やインジケータ等で DOM 階層をいじった時の必須チェックにする。

## 2026-07-13: 調査はローカルチェックアウトだけでなく origin/main と最近のPRも見る

- **何が起きたか**: 「キャラデータの編成順を使う」という依頼に対し、ローカルチェックアウト(古いフィーチャーブランチ)だけを調査して「編成順フィールドは存在しない」と報告した。実際には PR #8 で `formationOrder` が main にマージ済みで、ユーザーに2回指摘されて判明した。
- **ルール**: ユーザーが「データ/機能がある」と言ったら、ローカルに見つからなくても即座に否定しない。`git fetch` して origin/main との差分・最近のマージPR (`gh pr list --state merged`) を確認してから結論を出す。作業ブランチが main より遅れている可能性を常に疑う。
